# Live staging deployment: GitHub Pages demo + Render app + Neon

## Architecture

- **GitHub Pages** continues to serve the public, non-persistent UI demo.
- **Render Web Service** serves the *real authenticated React admin UI and Express
  API on the same HTTPS origin*. No cross-origin credentials, browser DB URLs,
  or public AI provider keys.
- **Neon PostgreSQL**, project `shiny-forest-27088168`, database
  `snapycall_pilot`, stores candidates, encrypted AI settings, drafts and audits.
- **No mail delivery endpoint** in this version.

The existing Express application remains the only runtime API implementation.
We do not create a second API or move the Prisma backend into another runtime.

## Provisioning

1. Connect the **Render** app to ChatGPT or open the Render Dashboard, select
   **New → Blueprint**, and select this GitHub repository.
2. Review `render.yaml` and create the staging service. It uses the Free plan,
   Frankfurt region and **manual deployment**.
3. During initial Blueprint creation provide the following secret environment
   variables in the Render Dashboard:
   - `DATABASE_URL`: Neon **pooled** PostgreSQL connection string for
     `snapycall_pilot`; used only by the server.
   - `DIRECT_URL`: Neon **direct** PostgreSQL connection string for the same
     database/role; used for Prisma migrations.
   - `ADMIN_EMAIL`: designated admin email address.
   - `ADMIN_PASSWORD_HASH`: a bcrypt cost 12 password hash. Generate on a
     trusted device (with Node and dependencies installed):
     `node -e "import('bcryptjs').then(m => m.default.hash(process.env.ADMIN_PASSWORD, 12).then(console.log))"`
     and supply ADMIN_PASSWORD only as a temporary local environment variable.
     Never add the raw admin password to GitHub or logs.
   - `SESSION_SIGNING_KEY` and `AI_ENCRYPTION_KEY` are **generated by Render**
     on initial creation; do not regenerate them across deploys.
4. Trigger a first manual staging deploy. The startup command applies tracked
   Prisma migrations using `DIRECT_URL`, then starts the same-origin server.
5. Confirm `GET /api/ready` returns HTTP 200 with
   `{"status":"ready"}`, and `GET /api/session` returns
   `{"authenticated":false}` for an anonymous client.
6. Log in with the admin account and verify candidate creation persists across
   page refresh. Configure a **test-only** AI key and generate a draft to verify
   the provider connection and key encryption; note this can incur provider costs.
7. Keep email sending disabled and do not import real third-party contacts before
   reviewing data provenance and lawful outreach basis.

## Release safeguards

- `autoDeployTrigger: off`: no production changes on GitHub merge.
- Keep service count to one instance; existing login rate limiting is
  process-memory based. A future multi-instance rollout needs a shared limiter.
- With Prisma migrations in startup, multiple instances are forbidden until
  a dedicated migration release phase is introduced.
- Render Free web services **sleep after inactivity**, restart with cold-start
  latency, and are not suitable for production SLAs.
- Do not use public GitHub Pages for admin passwords or API keys.
- Server passwords, signing keys, encryption keys and DB URLs must remain in
  Render service secrets, never in repository files or GitHub Pages assets.
- Rotating `AI_ENCRYPTION_KEY` without re-encryption will make saved provider
  API keys undecryptable.
- If changing `DATABASE_URL`, verify the same role/database/branch for both
  pooled and direct URLs before migrating. Otherwise migration history may
  be applied against the wrong database.

## Validation

`Pilot app CI` runs `npm ci`, unit tests, React typecheck,
Prisma schema validation, a clean-start migration against disposable
PostgreSQL 17, production build, and authenticated HTTP smoke.

A successful CI run **does not** prove the deployed Render service is live;
deployment status, /api/ready and authenticated UI smoke are separate gates.
